# ADR-114 — Backoffice Notification Administration

**Status:** Proposed — pending the operator's real build/unit/e2e verification run
**Context area:** 21_ADRs (Backend / Backoffice), Operational Readiness — Stage 7 of the Backoffice completion roadmap
**Related:** ADR-098/ADR-099 (Backoffice RBAC Foundation), ADR-060 (Notification Templates — the `NOTIFICATION_TEMPLATE_VIEW`/`MANAGE` pair this ADR's own pair is deliberately distinct from), ADR-039/ADR-088 (real async BullMQ dispatch + real Email/SMS/Push providers — the mechanism `resend` re-drives), ADR-102 (Backoffice Permission Migration Completion — the one-VIEW/MANAGE-pair-per-domain convention this stage follows), ADR-111/ADR-112/ADR-113 (User/Building/Financial Administration — Stage 4/5/6, the direct structural precedent this stage mirrors, with one deliberate module-placement deviation — see Decision below)

## Context

This is Stage 7 of the 10-stage Backoffice completion roadmap (Stages 1–6: Monitoring, Maintenance Mode/Feature Flags, Operational Dashboard, User/Building/Financial Administration, all Closed). A real-repo-state check for this stage looked for the same shape of gap Stages 4-6 each found and closed — a dormant, already-granted `PermissionKey` pair reserved but never wired to a route.

No such pair exists for this domain. `grep`ing the `PermissionKey` enum for every `NOTIFICATION_*` value found exactly two: `NOTIFICATION_TEMPLATE_VIEW`/`NOTIFICATION_TEMPLATE_MANAGE` (ADR-060/ADR-102) — and both are already fully wired, gating `NotificationTemplateController`'s real routes (`backoffice/notification-templates`), granted to `Technical Admin`. There is no unused Notification-domain key left to repurpose. Separately, there is no staff-facing surface at all today over `Notification`/`NotificationDelivery` — `NotificationsController`/`NotificationPreferencesController` are both scoped to the calling person's own inbox (`@CurrentUser()`), and no controller anywhere lets staff see who received what, on which channel, with what delivery outcome, across the whole platform — nor any way to react to a real dispatch failure (`NotificationRepository.markDeliveryFailed` has existed since ADR-027 with a real caller since ADR-088, but nothing has ever read a `FAILED` delivery back out, let alone re-driven it).

This stage closes both gaps together: it introduces the first genuinely new `PermissionKey` pair (and accompanying schema migration) since ADR-110's single `DASHBOARD_VIEW`, and gives staff a cross-recipient delivery list/detail view plus the one meaningful mutating action this domain actually has a real underlying mechanism for — resending a `FAILED` delivery through the same BullMQ pipeline every other delivery already goes through.

## Decision — Permission Keys: New, Not Reused (a break from Stages 4-6's own pattern)

`NOTIFICATION_DELIVERY_VIEW` / `NOTIFICATION_DELIVERY_MANAGE` — two new `PermissionKey` enum values, added to `prisma/schema.prisma` and `prisma/seed/rbac.seed.ts`, granted to `Technical Admin` (the same role that already owns `NOTIFICATION_TEMPLATE_VIEW`/`MANAGE` and every other platform-wide operational/system key — Scheduler, Feature Flags, Maintenance Mode, Monitoring, Dashboard).

Deliberately a **distinct** pair from `NOTIFICATION_TEMPLATE_VIEW`/`MANAGE`, not folded into it — the same "no permission shared across domains" boundary discipline every pair in `rbac.seed.ts` already follows (see e.g. `SUBSCRIPTION_VIEW`/`MANAGE`'s own comment on why it isn't folded into `FINANCE_VIEW`/`REFUND`). The Template pair governs what a notification *says* (staff-authored copy, edited rarely, platform-wide); this pair governs what actually got *sent* to a specific recipient and re-driving a failed send (operational, per-delivery, potentially high-volume) — different data, different risk profile, different natural reader (a template edit is a content change; a delivery resend is closer in kind to Building's Lock or Payment's Reverse).

This is the first stage since ADR-110 (`DASHBOARD_VIEW`) to require a real schema migration. Per the roadmap's own Verification Gate, this ADR cannot be marked Closed until the operator has run `npx prisma migrate dev`, `npx prisma generate`, and `npm run db:seed:rbac` on their own machine — see Build/Unit/E2E Verification below for the exact sequence and why this sandbox's own verification is structurally incomplete without it.

## Decision — Module Placement: `NotificationsModule`, Not `BackOfficeModule` (a deliberate deviation from ADR-111/ADR-112/ADR-113's own pattern)

Every prior Administration service/controller (`UserAdministrationService`, `BuildingAdministrationService`, `FinanceAdministrationService`) lives in `src/modules/backoffice/{application,controller}/`, registered in `BackOfficeModule`. This stage's `NotificationAdministrationService`/`NotificationAdministrationController` instead live in `src/modules/notifications/{application,controller}/`, registered in `NotificationsModule` — the physical location is the deviation, not the naming (`*AdministrationService`/`*AdministrationController` still follow the roadmap's own convention).

The reason is structural, not stylistic: `NotificationsModule` already imports `BackOfficeModule` (ADR-060, so `NotificationTemplateController` can reuse `PlatformRolesGuard`/`BackOfficeRepository` rather than invent a second platform-staff authorization mechanism). `BackOfficeModule` importing `NotificationsModule` back — which would be required to give a `backoffice/`-housed admin service access to `NotificationRepository`/`NotificationsService`/the BullMQ dispatch queue — would create a module cycle. NestJS supports breaking such cycles with `forwardRef()`, but that is a strictly worse option here than simply placing the new code in the module that already has everything it needs without any cycle at all: `NotificationsModule` already provides `NotificationRepository`, `NotificationsService`, and the registered `NOTIFICATION_DISPATCH_QUEUE`, and already imports `BackofficeRbacModule` for `PermissionsGuard` (ADR-102). `NotificationTemplateController` itself is the direct, pre-existing precedent for "a staff-facing Notification-domain controller lives inside `NotificationsModule`, not `BackOfficeModule`, and reuses the Backoffice guards via import" — this stage just applies that same precedent to a controller named with the newer `*AdministrationController` convention.

The route path is unaffected: `backoffice/notifications` (matching `NotificationTemplateController`'s own `backoffice/notification-templates`), so the URL surface stays consistent with every other Backoffice admin endpoint regardless of which module the file physically lives in.

## Decision — Endpoints

Three routes, added to `NotificationsModule`:

- `GET /api/v1/backoffice/notifications` — paginated (`page`/`limit`, ADR-072 convention), with `search` (case-insensitive `contains` across the parent Notification's `title` or the recipient's own `phone`/`fullName`), `status` (exact-match `NotificationDeliveryStatus`), `channel` (exact-match `NotificationChannel`), and `category` (exact-match `NotificationCategory`) filters. Gated `REVIEWER`+ + `NOTIFICATION_DELIVERY_VIEW`. The first cross-recipient query over `NotificationDelivery` in the codebase — `NotificationRepository.listForPerson`/`searchForPerson` are both single-recipient-scoped by design (the person-facing module never needed anything broader).
- `GET /api/v1/backoffice/notifications/:deliveryId` — delivery fields (channel/status/timestamps/failure reason) plus the parent notification's own title/body/category/priority/building/recipient/source-event context. Same gate as list. 404s on an unknown id.
- `POST /api/v1/backoffice/notifications/:deliveryId/resend` — mandatory `reason` (new `ResendNotificationDeliveryDto`). Only valid when the target delivery's `status` is `FAILED`; any other status 422s (`BUSINESS_RULE_VIOLATION`). Resets the delivery to `PENDING` and re-enqueues the exact same `dispatch-delivery` BullMQ job `notify()` uses (see Decision below for the one deliberate difference). Gated `SENIOR_REVIEWER`+ + `NOTIFICATION_DELIVERY_MANAGE`, matching this roadmap's own precedent for a consequential, side-effecting staff action (`BuildingAdministrationController.lock`, `FinanceAdministrationController.reverse`).

## Decision — Resend Reuses the Full BullMQ Dispatch Mechanism (ADR-113's full-domain-service-reuse pattern, applied to a brand-new method)

Resending a delivery is not a simple field write: `NotificationDispatchProcessor.process()` only proceeds when `delivery.status === 'PENDING'` (any other status is treated as "already handled, don't double-dispatch or overwrite a terminal status" and silently returns) — so a resend that only flipped the database row without also re-enqueueing a BullMQ job would never actually re-attempt delivery. A raw-repository-call pattern (ADR-111/ADR-112's own default shape) is not sufficient here; the real dispatch pipeline — the same one `NotificationsService.notify()` already drives, including its real Email/SMS/Push providers (ADR-088) — must run again.

`NotificationsService.resendDelivery(deliveryId)` is a new method, not an additive-parameter extension of an existing one (unlike ADR-113's `options.auditAction` pattern) — there is no pre-existing "resend" call site whose behavior needs preserving, since nothing in this codebase has ever re-driven a delivery before. It owns the full mechanical contract: look up the delivery, guard `status === 'FAILED'` (`NotFoundAppError` if missing, `BusinessRuleViolationError` otherwise), reset it to `PENDING` via a new `NotificationRepository.resetDeliveryForResend`, and re-enqueue the same `DISPATCH_DELIVERY_JOB` job with the same `attempts: 3`/exponential-backoff options `notify()` uses.

One deliberate difference from `notify()`'s own enqueue call: `notify()` sets a fixed `jobId: delivery.id` specifically so the same delivery can never be double-queued *during its own creation*. `resendDelivery` omits `jobId` entirely — reusing the same fixed id for a resend risks BullMQ treating the new job as a duplicate of the original, already-settled (failed) job and silently declining to actually run it again, which would make the resend action a no-op that still returns `200` — a much worse failure mode (invisible) than simply not deduplicating a deliberate, single, admin-triggered action. The service-layer `FAILED`-status guard is this action's own idempotency protection instead: once a resend succeeds, the delivery is `PENDING`, so an immediate second resend attempt (whether from a double-click or a genuine retry) is rejected with 422, not silently re-enqueued a second time.

`NotificationAdministrationService.resend` calls this method, then — on success only — records the distinctly-named audit action (`NotificationDeliveryResentByAdmin`) with the caller-supplied `reason`. Splitting it this way (mechanics in `NotificationsService`, staff attribution in `NotificationAdministrationService`) keeps `NotificationsService` free of any staff-actor-specific concept (`actorPersonId`/`requestId`/audit) it has never needed before, while still guaranteeing (per the unit test's own explicit assertion) that a rejected resend never produces an audit entry.

`list`/`getDetail` are the raw-repository-call pattern (ADR-111/ADR-112's own default) — two new `NotificationRepository` methods, `searchDeliveries`/`getDeliveryAdminDetail`, since these are pure reads with no business-rule policy or side effect to preserve.

## Implementation

- `prisma/schema.prisma` — `NOTIFICATION_DELIVERY_VIEW`/`NOTIFICATION_DELIVERY_MANAGE` added to the `PermissionKey` enum.
- `prisma/seed/rbac.seed.ts` — both keys added to `PERMISSIONS` and to `Technical Admin`'s grant list; `Technical Admin`'s `ROLE_DESCRIPTIONS` entry updated to mention notification delivery administration.
- `src/modules/notifications/infrastructure/repositories/notification.repository.ts` — three new methods: `resetDeliveryForResend` (the resend mutation), `searchDeliveries` (list/search/filter, same `where`-with-`undefined`-keys convention `BackOfficeRepository.searchPayments`/`searchBuildings` established), `getDeliveryAdminDetail` (the detail query).
- `src/modules/notifications/application/notifications.service.ts` — new `resendDelivery(deliveryId)` method (see Decision above).
- `src/modules/notifications/application/dto/resend-notification-delivery.dto.ts` — the new mandatory-`reason` DTO.
- `src/modules/notifications/application/notification-administration.service.ts` — new `NotificationAdministrationService`: `list`, `getDetail`, `resend`.
- `src/modules/notifications/controller/notification-administration.controller.ts` — new `NotificationAdministrationController`: the three routes.
- `src/modules/notifications/notifications.module.ts` — the new controller/service registered; the existing `BackOfficeModule` import's own doc comment extended to explain why this stage's admin code lives here instead (see Decision above).
- `test/helpers/e2e-identity.ts` — `NOTIFICATION_ADMINISTRATION: 28` added to `E2E_SUITE_ID`.

No change to `BackOfficeModule`, `BackOfficeRepository`, or any file under `src/modules/backoffice/` — this stage's entire implementation footprint is inside `src/modules/notifications/` plus the shared `prisma/`/`test/helpers/` files every stage touches.

## Testing

- `src/modules/notifications/application/notifications.service.spec.ts` — **new file**; `NotificationsService` itself predates this stage and had no prior unit spec, so this file is deliberately scoped to `resendDelivery` only (the single new method this stage adds), not a retroactive full-coverage spec for the rest of the class — that pre-existing gap is residual debt this stage inherits but does not introduce (see Risks below). Covers: the happy path (FAILED → reset + re-enqueue with no `jobId`, correct return shape); `NotFoundAppError` on a missing delivery; `BusinessRuleViolationError` for each of `PENDING`/`SENT`/`DELIVERED` (i.e. every non-`FAILED` status, via `it.each`) — and in every rejection case, neither the repository reset nor the queue `add` is called.
- `src/modules/notifications/application/notification-administration.service.spec.ts` — **new file**; `NotificationRepository`/`NotificationsService`/`AuditService` all fully mocked. Covers: `list`/`getDetail` pass filters/pagination through unmodified and `getDetail` 404s on an unknown id; `resend` delegates the mutation to `NotificationsService.resendDelivery` (never touches the repository's mutation method directly) and only records the `NotificationDeliveryResentByAdmin` audit entry (with the real `reason`, correct `metadata.channel`/`previousStatus`) after that call succeeds — including an explicit test that a rejected resend records **no** audit entry at all, and a test that a `buildingId: null` delivery is audited with `buildingId: undefined` (not `null`), matching this repository's own `??` convention elsewhere.
- `test/notification-administration.e2e-spec.ts` — **new file**; the first e2e coverage either new key has ever had. Two independent 401/403×2/403-no-grant/granted-live/revoked-live blocks (List & Detail on `NOTIFICATION_DELIVERY_VIEW`, Resend on `NOTIFICATION_DELIVERY_MANAGE`), against two `NotificationDelivery` rows seeded directly via Prisma (one `FAILED`, one already `SENT`) — direct seeding, not a real dispatch failure, since reaching a genuine `FAILED` delivery through the real pipeline would require an actual provider to exhaust three real BullMQ retries, not a practical or deterministic e2e setup. Functional assertions: `search`/`status` filter/paginate correctly; the detail response's shape; 404 on an unknown `deliveryId` (both list-detail and resend); a missing `reason` 400s on resend; resending the already-`SENT` delivery 422s (`BUSINESS_RULE_VIOLATION`) before ever touching the `FAILED` one; resending the `FAILED` delivery flips its `status` to `PENDING` and clears `failureReason` (verified via a direct `prisma.notificationDelivery.findUnique` read, the same technique `finance-administration.e2e-spec.ts` itself uses for its own reverse/refund assertions) and records `NotificationDeliveryResentByAdmin` with the real reason; and resending that same delivery again immediately afterward (now `PENDING`, not `FAILED`) correctly 422s again — the state-guard-as-idempotency-protection behavior the Decision section above describes.

## Build / Unit / E2E Verification

**This sandbox could verify meaningfully less for this stage than for ADR-111/ADR-112/ADR-113 (which added zero schema changes), but more than ADR-109 (two entirely new Prisma models).** Like ADR-108/ADR-110, this stage adds new `PermissionKey` enum values only — no new Prisma models, no new fields on an existing model with real delegate methods to fake. The same hand-patch technique those two ADRs established was reused, extended from one value to two: `node_modules/.prisma/client/index.d.ts`'s `PermissionKey` const object had `NOTIFICATION_DELIVERY_VIEW: 'NOTIFICATION_DELIVERY_VIEW'` and `NOTIFICATION_DELIVERY_MANAGE: 'NOTIFICATION_DELIVERY_MANAGE'` added by hand (type-only; this file is regenerated by the operator's own real `npx prisma generate` and is gitignored — never committed). This enabled a genuine, real in-sandbox verification pass:

- `npx eslint` on every new/changed file — clean after `--fix` (prettier-only formatting on the new files; `prisma/seed/rbac.seed.ts` retains the same pre-existing, out-of-scope prettier drift already documented since ADR-108, none of it on the lines this stage actually added).
- `npx tsc --noEmit` — **zero errors**, first attempt, across the full project including the new `test/notification-administration.e2e-spec.ts` file (confirmed separately, since `test/jest-e2e.json` is a `ts-jest` transform config, not a standalone `tsc` project file, and produces spurious decorator errors if invoked directly with `tsc -p`).
- `npm test` (full suite) — **595/595 passed, 50/50 suites**, including all 11 new tests across the two new spec files (`notifications.service.spec.ts` + `notification-administration.service.spec.ts`), on the first run, with no bug found.
- `npm run build` — succeeded (after moving aside a stale `dist/` directory the mounted filesystem could not overwrite in place, the same recurring device-bridge quirk noted since ADR-110).
- `npm run test:e2e` was **not** run in this sandbox — `NOTIFICATION_DELIVERY_VIEW`/`NOTIFICATION_DELIVERY_MANAGE` do not yet exist in the operator's real Postgres `PermissionKey` enum (only the local, type-only `.d.ts` hand-patch exists), so seeding a `Permission` row with either key would fail against the real database until the operator's own `npx prisma migrate dev` actually applies the new migration. Running e2e before that migration is applied would not be a meaningful signal — it is expected to fail for a reason entirely unrelated to this stage's code. Separately, no reachable Postgres/Redis exists in this sandbox at all (established since ADR-110).

**The operator must, in order, on their own machine:** `npx prisma migrate dev` (generates and applies the new migration adding `NOTIFICATION_DELIVERY_VIEW`/`NOTIFICATION_DELIVERY_MANAGE` to the real `PermissionKey` enum), `npx prisma generate` (this overwrites the local hand-patch above with the real generated client — expected and fine), `npm run db:seed:rbac` (idempotent — grants both new keys to `Technical Admin`), then `npm run build`, `npm test`, `npm run test:e2e`. This ADR is not Closed until that full sequence is confirmed green (or any failure has been triaged per the roadmap's own Verification Gate — isolated rerun, root-cause, compare against ADR-107's known patterns, before attributing anything to this stage).

## Non-Goals (Phase 1)

Explicitly out of scope for this ADR, listed exhaustively:

- Resending a delivery whose status is anything other than `FAILED` (including a bulk "resend all failed deliveries for this notification/recipient" action) — one delivery, one explicit staff decision, matching the roadmap's own "never build incomplete endpoints for high-risk operations" principle; a bulk variant is a materially different risk/idempotency surface not requested for this stage.
- Editing/creating `Notification`/`NotificationDelivery` rows directly, or a staff-facing "send an arbitrary notification to a recipient" broadcast tool — `NOTIFICATION_DELIVERY_MANAGE` here covers only resending a delivery the real event pipeline already created; a staff-authored broadcast is a different capability with its own design questions (recipient targeting, rate limiting, abuse potential) and was not requested for this stage.
- Any change to `NotificationTemplateController`/`NotificationTemplateService`/`NOTIFICATION_TEMPLATE_VIEW`/`MANAGE` — that surface is untouched; this stage adds a sibling domain, not a modification to the existing one.
- Adding `NotificationDeliveryResentByAdmin` to `CRITICAL_AUDIT_ACTIONS` (`dashboard.service.ts` remains out of this stage's scope — see Risks below, extending the same standing reconciliation list ADR-112/ADR-113 already flagged).
- A `sortBy`/`sortOrder` query parameter — following the same established convention every prior stage's list endpoint already uses (fixed `createdAt desc`).
- Real per-provider retry/backoff tuning, or surfacing BullMQ job/queue health (job counts, dead-letter inspection) through this or any Backoffice endpoint — `MONITORING_VIEW`'s existing system-health surface (ADR-108) is the closest existing concept and was not extended here; out of scope for this stage.

## Risks / Residual Debt

- **`CRITICAL_AUDIT_ACTIONS` reconciliation now has seven (not six) names waiting.** ADR-112/ADR-113 already flagged six names (`PersonSuspendedByAdmin`/`PersonReinstatedByAdmin`/`BuildingLockedByAdmin`/`BuildingReinstatedByAdmin`/`PaymentReversedByAdmin`/`PaymentRefundedByAdmin`) as absent from `dashboard.service.ts`'s allowlist; this stage adds `NotificationDeliveryResentByAdmin` to that same waiting list. Still a single small, separately reviewed change away from reconciling all seven at once.
- **`NotificationsService` has no unit spec beyond `resendDelivery`.** This stage's own new spec file is deliberately scoped narrowly (see Testing above) rather than retroactively covering `notify`/`markAsRead`/`archiveNotification`/etc. — a pre-existing gap this stage did not introduce and, per this engagement's "never touch out-of-scope areas" principle, did not attempt to close either. A future dedicated pass could add full coverage for the rest of the class.
- **No guard against resending a delivery whose recipient's notification preferences have since disabled that channel.** `notify()` itself checks `NotificationPolicy.isChannelEnabled` before ever creating a delivery for a given channel — a delivery that already exists (and later failed) was, by construction, channel-enabled at creation time. `resendDelivery` does not re-check the recipient's *current* preference before re-enqueueing, so a recipient who disabled (e.g.) SMS after a SMS delivery failed would still receive the resend. Accepted for this stage: re-checking live preference at resend time is a real design question (does a staff-initiated resend respect a preference change made after the fact, or does staff intent override it?) that was not asked and has no existing precedent in this codebase to resolve it against — named here rather than guessed at.
- **No cap on how old a `FAILED` delivery can be before a resend is rejected.** A delivery that failed weeks ago (e.g. because the parent `Notification`'s content is now stale/irrelevant) can still be resent — this stage did not add a staleness window, matching the "don't build ungrounded restrictions no source doc asked for" discipline this roadmap has followed throughout.

## Consequences

- Positive: staff gain the first cross-recipient view over `Notification`/`NotificationDelivery` in the codebase, and the first way to react to a real dispatch failure since ADR-088 made real provider failures possible.
- Positive: the resend mechanism reuses the exact real dispatch pipeline (`NotificationDispatchProcessor`, real Email/SMS/Push providers) rather than a parallel, simplified re-implementation — a resent delivery is indistinguishable, from the processor's point of view, from any other `PENDING` delivery, so it inherits every existing provider-fallback/stub behavior with zero new code in the processor itself.
- Positive: the state-guard (`FAILED`-only) doubles as this action's idempotency protection, with no separate idempotency-key mechanism needed — consistent with how Building's Lock/Reinstate and Finance's Reverse/Refund each rely on the target entity's own state transition for the same purpose.
- Neutral: this stage's entire implementation lives inside `NotificationsModule`, not `BackOfficeModule` — a deliberate, explained deviation from Stages 4-6's own module placement (see Decision above), not an inconsistency.
- Residual, tracked above: `CRITICAL_AUDIT_ACTIONS` reconciliation now covers seven names; `NotificationsService` unit coverage remains partial; no live-preference recheck or staleness window on resend.

## Future Review

- **`CRITICAL_AUDIT_ACTIONS` reconciliation.** Now covers seven names across four stages (see Risks above) — still a good, cheap, standalone candidate for a dedicated pass.
- **Bulk resend / broadcast tooling.** If a future requirement needs staff to resend more than one delivery at once, or send an arbitrary staff-authored notification, both deserve their own design pass — see Non-Goals above for why neither was built here.
- **Live-preference recheck on resend.** Named as an open question in Risks above, not designed now — revisited only if a real operational report of "a recipient who opted out was resent anyway" surfaces.
